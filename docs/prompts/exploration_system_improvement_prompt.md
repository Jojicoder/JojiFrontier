# プロンプト: 探索システムの改善案を出させる

このファイルはプロンプトそのもの。以下を丸ごとコピーして使う。

---

JOJIFrontier(C++/raylib製タクティクスRPG)の「探索システム」(戦闘前に毎回出る3択画面)
について、現状の実装を踏まえた具体的な改善案を提案してください。

## 設計意図(`docs/exploration_system.md`)

- 各地点で「通常選択肢2つ+兵種専用選択肢1つ」の3択を出す
- 兵種専用選択肢は常に最善にせず、安全・情報・戦利品・消耗・時間のトレードオフを持たせる
- 選択結果は敵の数・種類・初期配置・地形・開始HP・アイテム消費・追加戦利品・発見物・
  戦闘回避・ボス能力/増援条件のいずれかを変える
- 「兵種による探索能力」(辺境斥候=偵察/隠し道、辺境工兵=障害物、辺境猟兵=追跡、
  暁の衛生兵=医療、重装兵=瓦礫除去)を戦闘外でも価値を持たせる

## 実際の実装状況(2026-08-02時点の調査結果)

- `ui_exploration.cpp`は全地点で「A. 正面から進む/B. 崩落した脇道/C. 斥候ルート」の
  固定3択を表示する。UIの文言(効果説明テキスト)は灰枝の森だけ個別、他地域は汎用文言
  (`exploration.frontal_effect`等)を使い回す。
- `ExplorationOutcome`構造体(`include/jf/core/Exploration.hpp`)は7フィールド
  (partyDamage、enemiesRemoved、enableFreeDeployment、deploymentMaxColumn、
  restrictedAutoSpawnMaxColumn、extraBarrierCount、startingHeatLevel、
  enableReinforcementWave)しか持たず、**敵編成の入れ替え・戦利品/発見物の分岐・
  文章分岐には対応していない**(数値的な戦闘セットアップ調整のみ)。
- 本編62地点のうち、`routeOutcomes`(選択肢ごとの個別効果)を実際に定義しているのは
  **15地点だけ**。残りは全て共通の`cinderwatchOutcome(choice)`にフォールバックする
  (`Region.cpp:2489`)。しかもその15地点の中でも、3択のうち少なくとも1つが
  空の`ExplorationOutcome{}`(完全に無効果)になっているケースが複数ある
  (`quarryOldMineStage()`等)。
- 兵種専用ルート(`scoutRouteRequiredClass`)を個別に設定しているのも同じ15地点のみ。
  残りの地点は全て「辺境斥候がいるかどうか」というデフォルト条件1本で判定している
  (`ui_exploration.cpp`の`app.partyHasFrontierScout()`)。つまり「兵種による探索能力」の
  差別化は本編62地点の1/4未満でしか機能していない。
- `docs/implementation_status.md`はこれを自覚的な既知ギャップとして記録済み
  (「3つ目の探索選択はクラス未実装のため無効化」「選択したExplorationChoiceによって
  敵編成を出し分けられない」「兵種による探索能力の比較パネル/クールダウン表示は未着手」等)。
  つまり衰退ではなく、意図的なスコープ縮小のまま止まっている状態。
- 偵察網(`scout_network`施設)は実装済みで、解放すると選択前に敵編成が見える
  (`explorationEnemyPreview()`)。ただしルート選択そのものには影響しない(見えるだけ)。

## 依頼内容

上記の実装状況を踏まえ、次の観点それぞれについて具体的な改善案を提案してください。
「本来の設計をどこまで実現するか」だけでなく、「今の実装のまま何を足せば手触りが
良くなるか」という現実的な提案を歓迎します。

1. **選択肢の意味づけ**: 残り47地点(routeOutcomes未定義)に、どの程度・どんな粒度で
   個別効果を足すべきか。全地点に手作業で個別設定するのは非現実的という前提で、
   「地域ごとに共通する数種類のテンプレート効果」のような、労力対効果の良い中間案は
   考えられるか。
2. **兵種専用選択肢の拡張**: 現状は辺境斥候(ルートC)がデフォルトで、他の兵種
   (辺境工兵/辺境猟兵/暁の衛生兵/重装兵)は個別設定した15地点でしか出番がない。
   これを一般化する(例: パーティの兵種構成を見て、揃っていれば自動的に
   ふさわしいルートCの効果へ差し替える)ような仕組みは実現可能か。
3. **偵察網の活用強化**: 敵編成を見せるだけでなく、ルート選択の判断材料として
   もっと使えないか(例: 見えている敵構成によって危険選択の警告表示を変える等)。
4. **`ExplorationOutcome`の拡張**: 現状の7フィールド(数値調整のみ)に、敵編成の
   入れ替えや発見物の分岐を足す場合、既存の「Region.cppに直書き」という設計を
   崩さずに拡張する現実的な方法はあるか(データ駆動化するとどこまで複雑になるか)。
5. **UI/文言の底上げ**: 全地点で汎用文言を使い回している現状について、個別効果を
   増やさなくても文言だけ地域ごとに差し替える(比較的低コストな)改善はあるか。

各観点について「効果の大きさ」「実装コスト」「既存設計との整合性」を明記したうえで、
優先順位をつけて提案してください。
