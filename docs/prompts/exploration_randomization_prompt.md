# プロンプト: 探索選択肢のランダム化を設計させる

このファイルはプロンプトそのもの。以下を丸ごとコピーして使う。

---

JOJIFrontier(C++/raylib製タクティクスRPG)の探索画面(戦闘前に出る3択)を、
「毎回選択肢そのものが入れ替わる」仕組みへ拡張したい。設計案を具体的に提案してください。

## 現状の実装(2026-08-02時点)

- `ExplorationChoice`(`include/jf/core/Exploration.hpp`)は`FrontalAdvance`/
  `CollapsedSidePath`/`ScoutRoute`の3値固定のenum。UI(`ui_exploration.cpp`)は
  常にこの3つをA/B/Cのボタンとして表示する(ラベル・配置とも完全固定)。
- 効果(`ExplorationOutcome`)の決定方法は2段構え:
  1. 本編62地点中15地点は`StageDescriptor::routeOutcomes`で個別に手作りされた
     固有の3択(それぞれ物語文言付き)を持つ。
  2. 残り47地点は、stage.idの文字列パターンから8種類の地形テンプレート
     (森/山地/坑道/湿地/遺構/集落/砦/開けた荒野)のどれかを推定し
     (`explorationTemplateForStageId()`)、そのテンプレート固定の3択効果
     (`explorationTemplateOutcome()`)を使う。
- 兵種専用選択肢(C: 斥候ルート)は、地点ごとに`scoutRouteRequiredClass`
  (未設定ならテンプレートの既定兵種)を要求する。要求兵種が編成にいないと
  ボタンは無効化される。
- 効果は`ExplorationOutcome`の8フィールド(partyDamage、enemiesRemoved、
  enableFreeDeployment、deploymentMaxColumn、restrictedAutoSpawnMaxColumn、
  extraBarrierCount、startingHeatLevel、enableReinforcementWave)の数値調整のみ。
- 現状、探索専用の乱数源はコードに存在しない(全て決定論的)。

## やりたいこと

「その地点に到達するたびに、3つの選択肢の中身自体を再抽選する」機能を追加したい。
セーブ/ロード・再訪問のたびに毎回違う3択になってよい(再現性は不要)。

## 制約・方針(確定事項)

1. **既存15地点の手作り`routeOutcomes`(物語文言付きの固有選択肢)は、そのまま
   固定表示のままにする**。ランダム化の対象は、残り47地点(テンプレートに
   フォールバックしている地点)だけとする。
2. `ExplorationOutcome`構造体そのもの(8フィールド)は変更しない。抽選対象は
   あくまで「どの効果の組み合わせが3枠に入るか」であり、新しい種類の効果を
   増やすことは今回のスコープ外。
3. 3つのボタンという画面レイアウト(枠の数)は維持する。抽選で選ばれた
   選択肢が、この3枠それぞれに割り当てられる形にする。
4. 兵種専用選択肢の仕組み(特定兵種がいないと選べない)は今後も欲しいが、
   「常にC枠が斥候専用」ではなく、抽選で選ばれた選択肢自身が
   「特定兵種が必要」という情報を持つ形に一般化してよい。

## 依頼内容

1. **候補プールの設計**: 8つの地形テンプレートそれぞれについて、3枠へ抽選する
   候補を何個程度(5〜6個目安)用意すべきか。既存のテンプレート固定3択
   (正面/脇道/斥候)を候補の一部として含めつつ、新しい候補(効果の組み合わせ・
   兵種専用選択肢を含む)を具体的に何種類か提案してください。各候補について
   「効果(ExplorationOutcomeの値)」「必要兵種(あれば)」「表示文言案」を
   明記してください。
2. **抽選ロジックの構造**: 「地点到達のたびに候補プールから重複なく3つ抽選する」
   処理を、既存の`stageRouteOutcome(stage, choice)`(`Region.cpp`)というAPI形状を
   大きく崩さずに実装する場合、どんな関数・データ構造が必要か(例:
   `ExplorationChoiceOption`構造体、`rollExplorationChoices(template, seed)`関数等)。
3. **乱数源とタイミング**: 探索専用の乱数をどこで(`GameApp`か`ExpeditionState`か)
   いつ(地点に最初に到達した時か、画面を開くたびか)引くべきか。再訪問のたびに
   毎回変えたい(再現性不要)という要件を踏まえた具体案。
4. **UI側の変更点**: 現在A/B/Cの固定ラベル・固定位置で表示している
   `ui_exploration.cpp`を、抽選結果に応じた動的なラベル・効果表示へ変える場合の
   実装方針。
5. **テストへの影響**: 「毎回結果が変わる」設計を、既存のヘッドレステスト
   (`tests/test_battle.cpp`)でどう検証すべきか(例: 固定シードを注入できる形にして
   テストだけ決定論的に検証する等)。

各項目について、既存の「Region.cppに直書き」「ExplorationOutcomeは数値調整のみ」
という設計をなるべく崩さない範囲で、実装しやすい具体案を優先順位付きで提案して
ください。
